# FitCoach — AI-Powered Gym App

A workout companion that sets/tracks goals, logs sets & reps, and knows what you actually did — not what a template assumed you'd do. No fixed weekly split to fall behind on: it tracks what's overdue and how this week is actually going, and rebalances the plan live as your real behavior diverges from what you intended.

Stack: **Express + TypeScript** (backend), **React + TypeScript** (frontend), **AI API** (reasoning/coaching + catalog generation), **Postgres** (data), **YouTube Data API** (verifies real reference videos for whatever AI proposes).

Built for a solo dev with **~30 min/day**. This doc is both the architecture spec and the step-by-step build plan.

---

## 1. Requirements

### Product Requirements

The original feature list this app is built around, and where each is handled in the architecture below:

1. **User sets a goal, can modify it** — `Goal` model; `POST/GET /api/goal` (Phase 3).
2. **Track performance: sets, reps, weight** — `SetLog` model; `POST /sessions/:id/sets` (Phase 5).
3. **Track which body part was last trained, know what's next** — `BodyPartHistory` + staleness ranking inside `computeNextSessionPlan()` (§4, Phase 4).
4. **Skip an exercise or request an alternative** — `POST /sessions/:id/skip-exercise`; AI picks from a pre-curated `alternatives` list rather than inventing one (§4, Phase 6).
5. **Every exercise backed by a YouTube video for reference** — `Exercise.youtubeVideoId`, generated by AI and verified against the real YouTube Data API before it ever reaches the catalog (§4a, Phase 1).
6. **User can ask to focus on a different body part or combo** — free-text "change focus" resolved by AI to `bodyPart` enum values (Phase 6, 9).
7. **Ask how much time is available before each session (30 / 45 / 60 / no limit)** — `TimeBudgetPicker` → `exerciseCount(timeBudget)` (§4, Phase 4, 8).
8. **User picks a day-frequency plan (e.g. 3-day, 4-day/week), can change it mid-week, and the app accounts for what's actually been done in a rotating program** — originally modeled as a fixed `SplitTemplate` + `rotationCursor`; per the flexibility discussion above, this is now a rolling `WeeklyIntention` (soft weekly target) checked against the live count of completed `Session` rows, so mid-week changes and inconsistent weeks are handled by recomputation rather than a rotation cursor that can fall out of sync (§3 note, §4, Phase 3/4/9).

### Setup Requirements (before Phase 0)

- Node.js 18+ and npm or pnpm
- PostgreSQL instance (local, or a free tier on Supabase/Neon)
- An `ANTHROPIC_API_KEY`
- A YouTube Data API key (Google Cloud Console — free tier covers this volume of search calls)
- For deploy only (Phase 11): accounts on Render/Fly.io/Railway and Vercel/Netlify

## 2. Design Principles

1. **AI builds the catalog, but never invents a video link.** The exercise catalog isn't hand-typed by you — a one-time (then periodically re-run) pipeline has AI propose exercise names/metadata, and a separate step resolves each one against the real **YouTube Data API** to attach an actual, verified `videoId`. AI proposes; the API verifies. At runtime (during a workout), AI only ever picks *from that already-verified catalog* — it never generates a URL live. This is what keeps both the seeding and the day-to-day coaching hallucination-free.
2. **Deterministic core, LLM-assisted edges.** Planning logic (which body part is overdue, how to bundle when behind pace), time-budget-to-exercise-count, and set/rep logging are plain TypeScript — fast, testable, free. AI is invoked for: natural-language goal/focus changes, alternative-exercise suggestions with reasoning, and periodic plan commentary. This keeps the app functional even if the AI API is down.
3. **Small vertical slices.** Every phase below ends with something clickable/testable, sized for a 30-minute session.

## 3. Data Model (Postgres, via Prisma)

```
User
 ├─ id, email, passwordHash, createdAt
 ├─ Goal (1:1, editable)        → type: strength | hypertrophy | endurance | fat_loss, notes
 ├─ TrainingPreference (1:1)    → splitFlavor: full_body | upper_lower | push_pull_legs (a grouping preference, not a fixed calendar)
 └─ Session[] (1:many)

Exercise (catalog, generated by AI + verified via YouTube Data API — see §4a)
 ├─ id, name, bodyPart (enum: chest, back, legs, shoulders, arms, core, full_body)
 ├─ secondaryBodyParts[]
 ├─ equipment (barbell, dumbbell, machine, bodyweight, cable)
 ├─ youtubeVideoId, youtubeTitle, youtubeChannel   → all pulled from a real API response, never LLM-written
 ├─ source ("AI_generated" | "manual_override")
 └─ alternatives: Exercise[] (self-relation; pairs proposed by AI, still verified individually)

WeeklyIntention (one row per user per calendar week — this is what makes the plan "rolling" instead of fixed)
 ├─ userId, weekStartDate, targetSessions (e.g. "3 this week" — soft, editable anytime)
 └─ sessionsCompletedThisWeek is NOT stored — always derived live by counting `Session` rows in that week, so it can never drift out of sync with reality

Session (one workout instance)
 ├─ id, userId, date, timeBudgetMinutes (30|45|60|null)
 ├─ plannedBodyParts[], status (in_progress|completed|skipped)
 └─ SetLogs[] (1:many)

SetLog
 ├─ id, sessionId, exerciseId, setNumber, reps, weight, unit(kg/lb), completedAt

BodyPartHistory (derived/materialized for fast "what's overdue" lookups)
 ├─ userId, bodyPart, lastTrainedDate, lastSessionId
```

Why a `BodyPartHistory` table instead of computing from `SetLog` every time: the "what should I train next" query runs on every session start, so a small denormalized table (updated on session completion) keeps that endpoint trivial and fast.

Note what's gone from the old design: there's no `SplitTemplate` and no `rotationCursor`. Those assumed a fixed calendar ("Day 3 of your 4-day split") that breaks the moment someone's week goes off-script — which, per your point, is exactly what makes most gym apps feel rigid. Instead, "what's next" is computed fresh every time from two live signals: which body parts are actually stale (`BodyPartHistory`), and how the week is actually going relative to what was intended (`WeeklyIntention` vs. real `Session` count). See §4's planning logic below for how those combine.

## 4. Backend Architecture (Express + TypeScript)

```
/src
  /routes        → auth.ts, goals.ts, preferences.ts, sessions.ts, exercises.ts
  /services
     planning.ts        → pure functions: computeNextSessionPlan(bodyPartHistory, weeklyIntention, sessionsThisWeek, preference)
     timeBudget.ts      → pure functions: exerciseCount(timeBudget) 
     coach.ts           → wraps Anthropic SDK; builds prompts from structured state
  /db             → Prisma client + schema.prisma
  /middleware     → auth (JWT), error handler
  server.ts
```

### Key endpoints

| Method | Route | Purpose |
|---|---|---|
| POST | `/api/goal` | create/update goal |
| GET | `/api/goal` | fetch current goal |
| POST | `/api/preferences` | set split flavor (full_body/upper_lower/push_pull_legs) |
| POST | `/api/weekly-intention` | declare/update this week's target session count — editable anytime, mid-week included |
| GET | `/api/weekly-intention/status` | target vs. actual `Session` count so far this week |
| POST | `/api/sessions/start` | body: `{ timeBudget, focusOverride? }` → returns planned exercises |
| POST | `/api/sessions/:id/sets` | log a set `{ exerciseId, reps, weight }` |
| POST | `/api/sessions/:id/skip-exercise` | body: `{ exerciseId, reason? }` → returns alternative |
| POST | `/api/sessions/:id/complete` | closes session, updates `BodyPartHistory` |
| GET | `/api/exercises?bodyPart=` | catalog browse |

### Planning logic (the core "what's next" engine — plain TS, no LLM, no fixed calendar)

This is a rolling coverage problem, not a template lookup — every call recomputes from scratch off two live signals:

1. **Staleness ranking**: sort all body parts by `lastTrainedDate` in `BodyPartHistory`, oldest first. That's the base priority order — whatever's most overdue goes first, always.
2. **Pace awareness**: compare `WeeklyIntention.targetSessions` against the real count of `Session` rows this week so far. If the user is behind pace (e.g., wanted 3, has done 1, and it's already Friday), bundle *more* stale body parts into the remaining session(s) instead of spreading them thin — this is what keeps someone who missed two days from just permanently losing coverage of whatever was "supposed" to be trained that day.
3. **Grouping preference**: `splitFlavor` decides *how* to bundle the staleness-ranked list (e.g., push_pull_legs groups chest/shoulders/triceps together rather than pairing chest with legs) — it's a grouping heuristic applied on top of the ranking, not a calendar that dictates today's body part outright.
4. **Time budget** trims the final list to what actually fits (see `timeBudget.ts`).
5. Because there's no `rotationCursor` to advance or fall out of sync, this also means: skip a day, do an extra session, change your weekly target mid-week — next `sessions/start` call just recomputes fresh off current data. Nothing to "reset" or get stuck in a stale state.

Optional, low-effort addition once real usage data exists: if `WeeklyIntention.targetSessions` consistently overshoots actual sessions over several weeks, `coach.ts` can generate a one-line soft nudge ("you've been averaging 2x/week the last month — want me to plan around that instead of 4x?") — purely a suggestion, never auto-adjusts the target without the user confirming.

### AI's role (via `coach.ts`)

AI is called for four specific, narrow tasks — always with structured JSON in, JSON out (use tool calling / forced schema), never freeform exercise invention:

- **Natural-language focus change**: user types "let's hit legs and shoulders today" → AI maps free text to `bodyPart` enum values from a provided list → deterministic code takes it from there.
- **Alternative exercise reasoning**: given "skip squat, line too long," AI picks from the pre-curated `alternatives` list for that exercise (passed in the prompt) and gives a one-line rationale — it doesn't invent new exercises.
- **Preference customization**: user says "I want to focus more on arms" → AI adjusts `splitFlavor`/emphasis within the existing enum options rather than generating something novel.
- **Pace nudges**: occasional, opt-in commentary comparing declared vs. actual weekly frequency (see above) — never silent, never auto-applied.

This keeps token usage tiny (short structured prompts) and keeps a non-LLM fallback path for every feature if you want the app to work offline from AI.

### 4a. Catalog Generation Pipeline (bot-driven, not hand-seeded)

This runs as an offline script (`scripts/generateCatalog.ts`), not a request-time path — you run it once to populate the DB, and re-run it later to expand coverage (new equipment, new body parts). Two-stage, so nothing ever reaches the DB without a real, verifiable source:

1. **Stage 1 — AI proposes.** Prompt AI (structured/forced JSON output) to produce a batch of exercise entries: `name`, `bodyPart`, `secondaryBodyParts`, `equipment`, and 1–2 candidate `alternativeName`s per entry. No video info here — AI is only naming real, well-known exercises, which it's reliable at; it is never asked for a URL.
2. **Stage 2 — YouTube Data API resolves.** For each proposed exercise, call the official `youtube.search.list` endpoint with a query like `"{exerciseName} proper form tutorial"`, take the top result(s), and store the real `videoId`, `title`, and `channelTitle` returned by the API. If no reasonable result comes back (e.g., API returns nothing usable), mark the entry `needsReview` instead of guessing.
3. **Optional light QC pass:** before committing to the DB, print a diff (`exercise name → matched video title/channel`) so you can eyeball obviously-wrong matches in one pass — a few minutes of a 30-min session, not manual seeding of the whole catalog.
4. Store `alternatives` as verified `Exercise` records too — an alternative is only linked once it has passed through the same Stage 2 resolution as any other entry.

Net effect: you never type in exercise names or paste YouTube links yourself. AI drives content generation; the YouTube API is the source of truth for anything a user actually sees/clicks.

## 5. Frontend Architecture (React + TypeScript)

```
/src
  /pages     → Onboarding, Dashboard, SessionStart, ActiveSession, History, GoalSettings
  /components→ ExerciseCard (embeds YouTube), SetLogger, TimeBudgetPicker,
               WeeklyIntentionCard (target vs. actual, editable anytime), SkipDialog, BodyPartBadge
  /hooks     → useSession, useGoal, useWeeklyIntention
  /api       → typed fetch client (shared types package with backend — see §6)
  /state     → React Context or Zustand for active-session state
```

- **YouTube embeds**: `<iframe src="https://www.youtube.com/embed/{youtubeVideoId}">` per exercise — the field is stored directly from the YouTube Data API response (see §4a), no parsing needed at render time.
- **SetLogger**: simple stepper inputs for reps/weight, optimistic UI, POST on each set.
- **SkipDialog**: shows AI's suggested alternative with the "why," plus a manual "pick from list" fallback.

## 6. Shared Types

Put request/response types in a small shared package (`/packages/shared-types`) imported by both frontend and backend (works well with a monorepo — see §8 setup). This is the single highest-leverage TypeScript move here: it stops the two "30-minute sessions" from drifting out of sync with each other.

## 7. End-to-End Flow (one training session)

1. User opens app → `GET /api/weekly-intention/status` + `BodyPartHistory` → dashboard shows "2 of 3 sessions done this week — next up: legs (most overdue)".
2. User taps **Start Session** → prompted: 30 / 45 / 60 / No limit.
3. `POST /api/sessions/start { timeBudget }` → backend runs `planning.ts` (staleness ranking + pace check) + `timeBudget.ts` → returns ordered exercise list (e.g., 5 exercises for 45 min; more bundled in if the user is behind pace this week).
4. Each `ExerciseCard` shows name, YouTube embed, target sets/reps.
5. User logs sets via `SetLogger` → `POST /sessions/:id/sets` per set (autosave, no "submit workout" cliff-edge).
6. User hits **Skip** on an exercise (queue too long) → `POST /skip-exercise` → AI/alternatives-table returns substitute → new `ExerciseCard` swapped in.
7. Mid-session, user can tap **Change Focus** → free text ("more back today") → AI maps to body parts → remaining queue re-generated.
8. User taps **Finish** → `POST /complete` → `BodyPartHistory` updated; the week's actual session count is simply the count of `Session` rows, so it's already correct — nothing to "advance."
9. Any time, user can update this week's target ("only have time for 2 this week") via `WeeklyIntentionCard`; the next `sessions/start` call re-plans off the new target immediately, and past sessions already logged are unaffected.

## 9. What to Explicitly Defer (don't build in v1)

- Social features, leaderboards, sharing.
- Auto-progression algorithms (e.g., auto-increasing weight) — log data first, add smart suggestions once you have real history to reason over.
- Native mobile app — responsive web is enough to validate the concept.
- Multi-LLM comparison — one AI model, one prompt path, keep it simple until the core loop is proven.
